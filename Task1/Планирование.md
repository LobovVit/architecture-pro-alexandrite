## 1. Контекст и краткое резюме текущей архитектуры

### 1.1 Общая информация
Компания «Александрит» — производство ювелирных изделий (B2C + B2B API).

Дата подготовки: **2026-01-10**

Источник: описание задания + C4-схема (draw.io).

### 1.2 Архитектура (по модели C4)

**Контейнеры и хранилища:**
- Internet Shop (Vue / TS / ThreeJS) → Shop API (Spring Boot) → Shop DB
- CRM (Vue SPA) → CRM API (Spring Boot) → CRM DB
- MES (React SPA) → MES API (C#) → MES DB
- RabbitMQ — обмен событиями между MES API и CRM API
- Хранилище 3D-файлов — используется Shop API и MES API
- API users → MES API (расчёт цены, B2B)

**Основные потоки:**
- **B2C:** Customer → Shop → Shop API → MES (pricing) → RabbitMQ → CRM → события обратно в MES
- **B2B:** API user → MES → RabbitMQ → CRM → MES (операторы)

**Ключевые факты:**
- Расчёт цены: 2–30 минут (в MES)
- Инфраструктура: dev / release / prod, по 1 инстансу сервисов и БД
- CI/CD: dev — auto, release/prod — manual, E2E — ручные

## 2. Идентификация проблемных мест

### 2.1 Наблюдаемые проблемы

#### P-OBS-01. Потерянные и просроченные заказы
**Проявления:**  
клиенты не получают заказ, статусы «живут» месяцами.

**Вероятные причины:**
- рассинхронизация статусов между MES / CRM / Shop;
- отсутствие идемпотентности и гарантированной доставки сообщений;
- нет единого источника истины по заказу;
- отсутствует end-to-end наблюдаемость.

---

#### P-OBS-02. Деградация производительности MES
**Проявления:**  
медленная загрузка первой страницы даже после фильтров и пагинации.

**Вероятные причины:**
- неэффективные запросы и индексы;
- агрегации считаются «на лету»;
- нет read-модели или кеша;
- рост данных + конкурентный доступ операторов.

---

#### P-OBS-03. Деградация после открытия B2B API
**Проявления:**  
резкий рост заказов, жалобы партнёров.

**Вероятные причины:**
- отсутствие rate limit и изоляции B2B;
- тяжёлый pricing стал входной точкой;
- нет асинхронного SLA-механизма;
- один инстанс MES/CRM/очередей.

---

### 2.2 Потенциальные архитектурные риски

#### P-RISK-01. Single Point of Failure
1 инстанс каждого сервиса и БД → простой при сбое.

#### P-RISK-02. RabbitMQ без DLQ и контрактов
Риски дублей, потерь и «ядовитых» сообщений.

#### P-RISK-03. Долгие операции в онлайн-контуре
Таймауты API, деградация сервисов.

#### P-RISK-04. Отсутствие наблюдаемости
Проблемы выявляются только по жалобам.

#### P-RISK-05. Медленные релизы
Ручные E2E → заморозка продакшна.

#### P-RISK-06. Неоптимизированная БД
Рост данных → нелинейное падение производительности.

#### P-RISK-07. Размытый workflow заказа
Заказы «зомби», сложные ручные разборы.

## 3. Архитектурные инициативы и приоритизация

### 3.1 Приоритеты
- **P0** — стабилизация и контроль
- **P1** — масштабирование и устойчивость
- **P2** — процессы и качество релизов

---

### 3.2 Инициативы P0 (0–8 недель)

#### I-P0-01. Надёжная интеграция заказов
- DLQ, retries, TTL в RabbitMQ
- inbox-таблицы (идемпотентность)
- единый формат событий + correlationId

**Эффект:** заказы перестают теряться.

---

#### I-P0-02. End-to-end наблюдаемость
- метрики очередей и pricing latency
- трассировка и логирование
- дашборд SLA заказов

---

#### I-P0-03. Асинхронный расчёт цены
- очередь задач + worker pool
- API статуса job (QUEUED/RUNNING/DONE)
- контроль параллелизма

---

#### I-P0-04. Оптимизация MES дашборда
- keyset pagination
- индексы `(status, created_at)`
- материализация счётчиков

---

### 3.3 Инициативы P1 (2–6 месяцев)

- устранение SPOF (2+ инстанса)
- read-replica БД
- API Gateway для B2B
- формализация workflow заказа

---

### 3.4 Инициативы P2

- автоматизация E2E
- контрактные тесты
- нагрузочное тестирование

---

## 4. Логика приоритизации

1. Бизнес уже теряет деньги → сначала надёжность
2. Самый дорогой этап — pricing
3. MES дашборд влияет на скорость производства
4. Масштабирование без контроля усилит хаос
