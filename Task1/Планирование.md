Планирование — анализ, идентификация проблем и поиск решений (Task1)
Компания «Александрит» — производство ювелирных изделий (B2C + B2B API)
Дата: 2026-01-10

Источник: описание задания + C4-схема (draw.io). Ниже — список проблем, инициативы и приоритизация.


1. Краткое резюме текущей архитектуры (по C4)


Контейнеры/хранилища:
- Internet Shop (Vue/TS/ThreeJS) -> Shop API (Spring Boot) -> Shop DB
- CRM (Vue SPA) -> CRM API (Spring Boot) -> CRM DB
- MES (React SPA) -> MES API (C#) -> MES DB
- Messages Queue (RabbitMQ): обмен событиями/сообщениями между MES API и CRM API
- 3D files storage: используется Shop API и MES API
- API user -> MES API (для расчёта цены и работы партнёров)

Основные потоки:
- B2C: Customer -> Internet Shop -> Shop API -> (Shop DB + 3D storage) -> MES API (расчёт) -> RabbitMQ -> CRM API (создание/ведение заказа) -> обратно событиями в MES
- B2B: API user -> MES API (расчёт) -> RabbitMQ -> CRM API (создание заказа) -> далее MES (операторы) и CRM (продавцы/админы)

Важно:
- Расчёт цены выполняется в MES (2–30 минут в зависимости от сложности 3D).
- Инфраструктура: 3 окружения (dev/release/prod), по 1 инстансу каждого приложения, БД — managed single-instance (чтение/запись на одном).
- CI/CD: dev auto, release/prod manual. E2E — ручные, гейтят прод.


2. Идентификация проблемных мест


Ниже — «наблюдаемые» (из симптомов) и «потенциальные» (архитектурные/инфраструктурные) проблемы.

-------------------------
2.1 Наблюдаемые проблемы
-------------------------

P-OBS-01. Просроченные и “потерянные” заказы (клиенты не получают заказ, статусами “живут” месяцами).
Вероятные причины:
- рассинхронизация статусов между системами (MES/CRM/Shop) при сбоях интеграции;
- отсутствие гарантированной доставки/идемпотентности/повторов и корректной обработки дублей;
- отсутствие единого источника истины по заказу и правилам переходов статусов;
- отсутствие наблюдаемости по «жизненному циклу заказа» end-to-end.

P-OBS-02. Деградация производительности MES (первая страница/дашборд грузится долго даже после фильтров и пагинации).
Вероятные причины:
- запросы к БД без правильных индексов / неоптимальные JOIN/агрегации;
- «дашборд по статусам» считается на лету по большой таблице заказов;
- нет оптимизированной read-модели/кэша/материализованных представлений;
- одновременно растут и объём данных, и конкурентный доступ операторов.

P-OBS-03. Резкое ухудшение после открытия B2B API (скачок входящих заказов, рост жалоб партнёров).
Вероятные причины:
- нет rate limit/квот/изоляции B2B от B2C;
- расчёт цены (тяжёлая операция) стал «входными воротами» и создаёт очередь ожидания;
- нет механизма “асинхронного расчёта с колбэком/пуллингом” и чётких SLA;
- один инстанс MES API/CRM API/очереди — узкое место по throughput.

-------------------------
2.2 Потенциальные проблемы (риски)
-------------------------

P-RISK-01. Single Point of Failure: по 1 инстансу каждого приложения и БД.
Последствия: любой сбой = простой, накопление очередей, нарушение сроков, “потеря” сообщений без DLQ.

P-RISK-02. RabbitMQ без явных DLQ/TTL/ретраев/идемпотентности и без «контрактов событий».
Последствия: дубли, потери, “ядовитые” сообщения, бесконечные ретраи, несогласованность статусов.

P-RISK-03. Длительные операции (расчёт цены до 30 минут) выполняются в “онлайн”-контуре без нормальной оркестрации.
Последствия:
- таймауты API, исчерпание пулов потоков/соединений, деградация всего сервиса;
- невозможность прогнозировать сроки, отсутствие прогресса/очереди/приоритизации.

P-RISK-04. Нет «end-to-end» мониторинга по заказу: метрик очередей, latency расчёта, SLA по статусам, трассировки.
Последствия: проблемы обнаруживаются по жалобам, нет быстрой локализации.

P-RISK-05. Релизы тормозятся ручным E2E и отсутствием прогонов на уровне интеграции/контрактов.
Последствия: рост техдолга, “заморозка” продакшна, невозможность быстро чинить.

P-RISK-06. База данных без масштабирования чтения/записи и без оптимизации под отчётные/дашбордные запросы.
Последствия: рост данных = нелинейное падение производительности.

P-RISK-07. Неясные правила переходов статусов в распределённой системе (workflow размазан по 3 системам).
Последствия: “заказы-зомби” в промежуточных состояниях, сложные ручные разборы, дорогие исправления.


3. Инициативы (что делать) + приоритизация


Ниже инициативы сгруппированы и отсортированы по приоритету.
Обозначения:
- P0 — остановить потери денег/контрактов, вернуть предсказуемость и контроль.
- P1 — масштабирование и устойчивость, чтобы рост нагрузки не приводил к повторению инцидентов.
- P2 — улучшения процесса разработки и качество релизов.

-------------------------
P0 (0–8 недель): стабилизация заказов и наблюдаемость
-------------------------

I-P0-01. Ввести “Order Reliability” контур для интеграции: гарантированная доставка + идемпотентность.
Что сделать:
- Для сообщений RabbitMQ: DLQ, retry policy, TTL, отдельные очереди по типам событий.
- В CRM API и MES API: «inbox» таблица (идемпотентная обработка по messageId/correlationId), чтобы дубли не ломали состояния.
- Ввести correlationId (orderId) и единый формат событий: OrderCreated, PriceCalculated, ManufacturingApproved, etc.
Результат: перестаём “терять” и “двоить” заказы, появляется управляемость.

I-P0-02. End-to-end наблюдаемость по заказам и очередям.
Что сделать:
- Метрики: очередь/лаг RabbitMQ, время расчёта цены, время нахождения заказа в каждом статусе, доля ошибок обработки.
- Трассировка/логирование с correlationId.
- Дашборд “Order SLA”: топ просроченных заказов, где “застряло”, какой компонент виноват.
Результат: проблемы видно за минуты, а не по жалобам.

I-P0-03. Перевести расчёт цены в асинхронную очередь задач внутри MES (worker pool) + API для статуса.
Что сделать:
- MES API принимает запрос, кладёт задачу в очередь (внутреннюю или RabbitMQ), возвращает jobId.
- Клиент (Shop/API user) получает статус: QUEUED/RUNNING/DONE/FAILED и результат цены.
- Ограничение параллелизма и приоритеты (B2C выше B2B или наоборот — решается бизнесом).
Результат: не убиваем API долгими запросами, повышаем throughput и предсказуемость.

I-P0-04. “Горячая” оптимизация главной страницы MES (самые новые заказы).
Что сделать:
- Перейти на keyset pagination (по createdAt/id), сортировка “новые сверху”.
- Индексы по (status, createdAt), (assignedOperator, status), (createdAt) в MES DB.
- Вынести агрегацию по статусам в материализованную таблицу/кэш (обновление по событиям).
Результат: операторы видят новые заказы быстро; снижается нагрузка на БД.

-------------------------
P1 (2–6 месяцев): масштабирование и устойчивость
-------------------------

I-P1-01. Убрать SPOF: минимум 2 инстанса каждого API за балансировщиком + health-check + авто-рестарт.
Что сделать:
- Stateless сервисы: сессии в shared storage/redis (если нужно), конфиги через env/secret manager.
- Поднять минимум 2 EC2/VM на сервис; или перейти на контейнеризацию + managed orchestrator.
Результат: отказоустойчивость, увеличение throughput без переписывания.

I-P1-02. Масштабирование БД и разделение чтение/запись там, где критично.
Что сделать:
- read-replica для отчётных/дашбордных запросов (MES/CRM).
- Настройка connection pooling, лимитов, slow query log.
Результат: дашборды не “садят” транзакционную нагрузку.

I-P1-03. Ввести API Gateway для B2B: квоты, rate limiting, ключи/планы, изоляция трафика.
Что сделать:
- Разные лимиты для партнёров, защита от “заливки” тяжёлыми моделями.
- Технические ответы: 202 Accepted для асинхронного расчёта, 429 при превышении квоты.
Результат: B2B перестаёт ломать B2C и внутренние процессы.

I-P1-04. Определить и реализовать “единый workflow заказа” как доменную модель (без полного переписывания).
Подход:
- Либо “Order Orchestrator” сервис (легковесный), который хранит состояние и публикует события.
- Либо чёткий контракт: CRM — источник истины по заказу, MES — по производству, Shop — по инициированию.
Результат: меньше рассинхронизаций и ручных разборов.

-------------------------
P2 (параллельно, 1–6 месяцев): ускорение релизов и качество
-------------------------

I-P2-01. Автоматизировать E2E (smoke/regression) в release окружении и сделать “release candidate” процесс.
Что сделать:
- QA + 1 backend/devops помогают поднять автотесты критичных сценариев.
- Гейты: unit + contract tests + минимальный smoke.
Результат: релизы чаще, фиксы быстрее, меньше “заморозки” прод.

I-P2-02. Контрактное тестирование интеграции (CRM<->MES<->Shop) и версионирование событий.
Результат: меньше инцидентов после изменений формата сообщений/API.

I-P2-03. Нагрузочное тестирование и capacity planning (особенно для расчёта цены и дашбордов).
Результат: понятный предел системы и план масштабирования.


4. Логика приоритизации (почему так)


1) Сейчас бизнес уже теряет деньги (контракты) => сначала устраняем причины “пропажи заказов” и даём прозрачность.
2) Самый дорогой узел — расчёт цены (2–30 минут) => переводим в контролируемую асинхронную обработку.
3) MES дашборд тормозит работу операторов => быстрые оптимизации БД/пагинации дают быстрый эффект.
4) Далее убираем SPOF и вводим масштабирование, иначе любая новая волна заказов повторит кризис.
5) После стабилизации — ускоряем релизы (автотесты/контракты), чтобы не жить месяцами без прод-фиксов.


5. Целевая архитектура через 6 месяцев (видение)


Цель: система выдерживает рост заказов, не “теряет” их и даёт предсказуемые сроки.

Как выглядит через 6 месяцев (реалистично для текущей команды):
- Асинхронный “Pricing pipeline”: MES API принимает, ставит задачу, воркеры считают, результат публикуется событием и доступен по API.
- Интеграция по событиям стала надёжной: DLQ/ретраи/идемпотентность, единые контракты событий, корреляция по orderId.
- Наблюдаемость: дашборды SLA по статусам, мониторинг очередей и длительности расчёта, алерты.
- Горячие read-модели: главная страница MES работает быстро (keyset pagination, индексы, кэш/материализация статусов).
- Минимум 2 инстанса ключевых API за LB, базовые авто-скейл правила.
- B2B трафик изолирован (API Gateway, квоты), чтобы партнеры не “кладут” производство и B2C.
- Релизы: автоматизированный smoke + часть регресса, чтобы выпускать фиксы быстро.


6. Если сделать только 3 пункта за полгода — что выбрать


1) I-P0-01 + I-P0-02 (как единый пакет): Надёжная интеграция + наблюдаемость.
Почему:
- прямо бьёт в “потерянные/застрявшие” заказы и даёт управляемость;
- позволяет быстро находить виновный компонент и чинить без угадываний.

2) I-P0-03: Асинхронный расчёт цены (очередь задач + worker pool + API статуса).
Почему:
- главный источник деградации под ростом нагрузки;
- уменьшает таймауты и разгружает API, делает throughput управляемым.

3) I-P0-04 (+ часть I-P1-02 при необходимости): Оптимизация MES дашборда для “самых новых заказов”.
Почему:
- напрямую влияет на скорость взятия заказа в работу и на мотивацию операторов;
- быстрый эффект (индексы/пагинация/материализация), снижает нагрузку на БД.

Примечание: “2 инстанса всего” (I-P1-01) очень желательно, но если выбирать строго 3, то сначала нужно перестать терять заказы и разрулить долгие операции. Масштабирование без надёжной интеграции будет лишь быстрее воспроизводить хаос.


7. Замечания по ресурсам команды (кто нужен)


Чтобы выполнить P0–P1 в срок, потребуются:
- DevOps: усиление (хотя бы 0.5–1 FTE дополнительно) на LB/масштабирование/мониторинг/CI.
- QA: выделить время на автотесты (P2-01), иначе релизы будут продолжать тормозить.
- Backend (C# + Java): совместно проработать контракты событий, идемпотентность и pipeline расчёта.
