# Архитектурное решение по логированию в системе «Александрит»

## 1. Контекст и цель

Сейчас разбор ошибок и нестандартных ситуаций часто выполняется «со слов клиента», потому что:
- нет единого места, где видно историю действий по заказу;
- логи разрознены и/или отсутствуют ключевые события;
- поддержке и разработчикам сложно сопоставлять события между системами (Shop / CRM / MES / RabbitMQ).

Цель решения:
- сделать разбор проблем **повторяемым и быстрым**,
- снизить нагрузку поддержки,
- повысить предсказуемость SLA по заказам,
- подготовить базу для алертинга и анализа аномалий.

---

## 2. Какие системы покрываем сбором логов (по C4)

Логи собираем из всех компонентов, где заказ может «сломаться» или зависнуть:

1) **Online Shop API (Spring Boot)**  
2) **CRM API (Spring Boot)**  
3) **MES API (C#)**  
4) **Фоновые обработчики / воркеры** (расчёт стоимости, обработка сообщений очереди)  
5) **RabbitMQ** (системные логи брокера + события DLQ/reties на уровне приложений)  
6) **Базы данных** (slow query log / audit log по необходимости)  
7) **S3-хранилище** (аудит-логи доступа + ошибки загрузки/скачивания на стороне приложений)  
8) **Ingress/LB** (доступные access logs, если есть — для корреляции и расследований)

> На схеме нужно отметить источники логов (1–8).  
> В текущей C4-диаграмме в первую очередь отмечаем: Shop API, CRM API, MES API, RabbitMQ, DB, S3.

## 3. Какие логи собирать (минимум INFO-событий)

Ниже список **обязательных INFO-логов** (событийных) — они должны формировать «таймлайн заказа».

### 3.1 Общие принципы форматирования
- Только **структурированные логи** (JSON).
- В каждый лог добавляем корреляционные поля:
  - `trace_id` / `span_id` (если есть трейсинг),
  - `correlation_id` (всегда),
  - `order_id` (если событие относится к заказу),
  - `request_id`,
  - `service`, `env`, `version`.

### 3.2 Online Shop API — INFO
1) `order_initiated` — создан INITIATED  
   Поля: customer_id (или anon_id), order_id, channel=b2c, cart_size  
2) `file_uploaded` — загружен файл/создана 3D-модель  
   Поля: order_id, file_id, file_size, polygon_count_bucket (если известно), upload_time_ms  
3) `order_submitted` — SUBMITTED  
   Поля: order_id, customer_id, items_count, model_ref  
4) `pricing_requested` — отправлен запрос в MES на расчёт  
   Поля: order_id, correlation_id, target=mes, payload_size  
5) `pricing_result_received` — получен ответ (если синхронно) / `pricing_job_created` (если асинхронно)  
   Поля: order_id, price, currency, duration_ms, result=success/fail

### 3.3 MES API + воркеры — INFO
1) `pricing_job_queued` — задача на расчёт поставлена в очередь  
   Поля: order_id, message_id/job_id, model_complexity, polygon_count_bucket  
2) `pricing_started` — расчёт начат  
   Поля: order_id, worker_id, started_at  
3) `pricing_completed` — PRICE_CALCULATED  
   Поля: order_id, duration_ms, price, result=success/fail, error_type (если fail)  
4) `order_list_view_loaded` — запрос первой страницы (операторы)  
   Поля: operator_id, filters, page_size, latency_ms  
5) `manufacturing_started` — MANUFACTURING_STARTED  
   Поля: order_id, operator_id  
6) `manufacturing_completed` — MANUFACTURING_COMPLETED  
   Поля: order_id, operator_id, duration_ms  
7) `packaging_started` / `shipped`  
   Поля: order_id, operator_id, tracking_id (если есть)

### 3.4 CRM API — INFO
1) `order_created_from_mes` — заказ создан в CRM из сообщения  
   Поля: order_id, correlation_id, source=b2b/b2c, partner_id (если b2b)  
2) `manufacturing_approved` — MANUFACTURING_APPROVED  
   Поля: order_id, seller_id, approved_at  
3) `order_closed` — CLOSED  
   Поля: order_id, reason=carrier/manual, closed_by, closed_at

### 3.5 Интеграция (RabbitMQ) — INFO на стороне приложений
1) `message_published`  
   Поля: exchange, routing_key, message_id, correlation_id, order_id, type, size_bytes  
2) `message_consumed`  
   Поля: queue, message_id, correlation_id, order_id, type, attempt  
3) `message_retried`  
   Поля: message_id, attempt, next_delay_ms  
4) `message_dead_lettered`  
   Поля: queue, dlq, message_id, reason, correlation_id, order_id

### 3.6 Уровни логирования помимо INFO
- **WARN**: деградации и нестандартные ситуации без падения:
  - превышение SLA на расчёт (например > 10 минут),
  - превышение таймаута вызова зависимого сервиса,
  - повторная обработка дубля сообщения,
  - попытки доступа без прав (не PII, а факт).
- **ERROR**: ошибки, влияющие на выполнение сценария:
  - HTTP 5xx,
  - ошибки сериализации/десериализации сообщения,
  - ошибка записи в БД,
  - невозможность отправить/прочитать из RabbitMQ,
  - ошибка доступа к S3.
- **DEBUG/TRACE**: включаем **временно** для точечной диагностики (по feature flag / runtime config),
  - строго ограничиваем объём,
  - не включаем в prod «навсегда».

## 4. Мотивация (что даст логирование)

### 4.1 Бизнес-эффект
- Сокращение времени ответа поддержки клиентам и партнёрам (B2B).
- Быстрое выявление причин просрочек => снижение потери контрактов.
- Прозрачность и доказательная база при спорных ситуациях (кто, когда, что сделал).

### 4.2 Технический эффект
- Уменьшение MTTR за счёт корреляции событий.
- Возможность строить алерты «по факту» (DLQ, ошибки, SLA).
- Быстрая диагностика деградаций (MES dashboard, pricing pipeline).

### 4.3 Метрики, на которые влияет внедрение
1. MTTR (mean time to resolve)  
2. MTTD (mean time to detect)  
3. % заказов с нарушенным SLA  
4. Количество обращений в поддержку на 1000 заказов  
5. Доля заказов, требующих ручного расследования

## 5. Приоритет внедрения: где сначала логирование и трейсинг

Команда не сможет покрыть всё сразу, поэтому приоритет следующий:

### P0 (сразу)
1) **MES API + воркеры (расчёт стоимости)**
   - главный узел задержек и деградации
2) **CRM API**
   - ключевой источник истины по заказу и его бизнес-статусам
3) **Интеграция RabbitMQ (продюсеры/консьюмеры)**
   - место, где сообщения теряются/дублируются

### P1 (следом)
4) **Online Shop API**
   - важен для B2C, но основные “зависания” после SUBMITTED происходят дальше
5) **Ingress/LB + инфраструктура**
   - для расследований и корреляции инцидентов

## 6. Предлагаемое решение

### 6.1 Стек (предпочтительный для MVP)
**Loki + Promtail + Grafana** (или Grafana Alloy)  
Почему:
- быстро поднимается, дешевле по ресурсам, удобен в связке с Grafana/Prometheus;
- хорошо подходит как «система анализа логов» для небольшой команды.

Альтернатива для расширения:
- OpenSearch (или ELK), если нужен мощный полнотекстовый поиск, долгий ретеншн и большой объём логов.

### 6.2 Архитектура сбора
1) Все сервисы пишут **JSON-логи в stdout** (K8s best practice).
2) Агент на ноде (Promtail/Alloy/Fluent Bit) собирает логи по namespace/app labels.
3) Агент добавляет метаданные: pod, namespace, node, env, app, version.
4) Логи отправляются в Loki/OpenSearch.
5) Grafana даёт:
   - поиск по `order_id/correlation_id/trace_id`,
   - сохранённые запросы,
   - дашборды (ошибки/аномалии/SLA).

### 6.3 Что отразить на схеме (новые элементы)
- Log Agent (Promtail/Fluent Bit) рядом с узлом исполнения (EC2/K8s node)
- Log Storage (Loki/OpenSearch)
- Grafana (UI для поиска и дашбордов)
- Связи: сервисы → agent → storage → Grafana

> В рамках задания нужно обновить C4-диаграмму (новые элементы выделить цветом по требованиям ревьюера).

## 7. Безопасность логов (PII/доступ)

### 7.1 Работа с чувствительными данными
- Запрещаем писать в логи:
  - ФИО, адреса, телефоны, email (в явном виде),
  - содержимое файлов/3D-моделей,
  - токены/ключи/пароли.
- Маскирование: частичное хэширование идентификаторов пользователя (если нужно).
- Allow-list подход: логируем только заранее определённые поля.

### 7.2 Доступ
- Доступ к Grafana/Loki/OpenSearch только через VPN/внутреннюю сеть.
- RBAC:
  - Support: чтение + готовые дашборды
  - Engineers: чтение + создание запросов/дашбордов
  - Admin: управление пользователями/ретеншн/индексы
- Аудит: логируем входы/действия админов в системе логов.

## 8. Политика хранения (ретеншн, индексы, размер)

### 8.1 Разделение
- Отдельный логический поток/лейбл/индекс на сервис:
  - shop-api
  - crm-api
  - mes-api
  - workers
  - rabbitmq
- Отдельно — security/audit logs (ограниченный доступ).

### 8.2 Ретеншн (рекомендация)
- ERROR/WARN: 30–90 дней (для расследований и трендов)
- INFO (событийные): 14–30 дней (или 60 дней, если SLA-споры часты)
- DEBUG: 1–3 дня и только временно (по инциденту)

> Реальные цифры уточняются после оценки объёмов (GB/day).

## 9. Из «сбора» в «анализ»: алертинг и аномалии

### 9.1 Нужен ли алертинг?
Да, минимальный набор алертов обязателен:
- рост ERROR rate по сервису,
- появление DLQ-сообщений,
- резкий рост `pricing_failed`,
- рост latency на критичных эндпойнтах (через метрики, но можно дублировать логами).

### 9.2 Поиск аномалий
Нужен как минимум на уровне эвристик:
- резкий всплеск `order_submitted` или `pricing_requested` (возможный DDoS / партнёр «заливает»),
- рост дублей `message_consumed` с одинаковым message_id,
- рост времени в статусе (по логам статусов, либо лучше через отдельные метрики).

Реализация:
- правила в Grafana Alerting,
- либо отдельный job, который агрегирует события и пишет метрики.

## 10. Дополнительное задание: критерии выбора технологии логов

Ниже критерии (≥5) и сравнение вариантов.

| Критерий | ELK (Elastic) | OpenSearch | Loki | Splunk |
|---|---|---|---|---|
| Лицензия | Elastic License (ограничения) | Apache 2.0 | AGPL/Apache (зависит от сборки), обычно open-source | Проприетарная |
| Стоимость владения | Средняя/высокая | Средняя | Низкая/средняя | Очень высокая |
| Масштабирование и объём | Отлично при правильной настройке | Хорошо | Хорошо для “logs as labels + content” | Отлично |
| Полнотекстовый поиск | Очень мощный | Мощный | Ограниченный (лог-строки, лучше по labels) | Мощный |
| Интеграция с Grafana/Prometheus | Хорошо | Хорошо | Отлично (нативно) | Через коннекторы |
| Сложность эксплуатации | Высокая (кластер, шарды, ретеншн) | Средняя/высокая | Низкая/средняя | Средняя, но закрытая экосистема |
| Подходит для MVP маленькой команды | Иногда тяжеловат | Да | **Да (оптимально)** | Нет |

**Выбор для MVP:** Loki (быстро, дешево, просто)  
**Выбор для роста:** OpenSearch/ELK, если критичен полнотекстовый поиск и большие ретеншны.

## 11. Итог

Внедрение централизованного структурированного логирования:
- ускорит расследования по заказам (по `order_id/correlation_id/trace_id`),
- снизит нагрузку поддержки,
- станет основой для алертинга и контроля SLA,
- подготовит систему к росту и переходу в Kubernetes.
