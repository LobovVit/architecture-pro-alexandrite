# Выбор и настройка мониторинга в системе «Александрит»

## 1. Контекст

Компания «Александрит» эксплуатирует распределённую систему, состоящую из:
- онлайн-магазина (B2C),
- CRM для работы с клиентами и заказами,
- MES для расчёта стоимости и управления производством,
- асинхронной интеграции через RabbitMQ,
- B2B API для внешних партнёров.

Рост нагрузки, открытие API и увеличение количества заказов привели к:
- потере заказов и рассинхронизации статусов,
- деградации производительности MES,
- отсутствию прозрачности для бизнеса и инженеров.

## 2. Мотивация

Мониторинг необходим компании по следующим причинам:

### 2.1 Для бизнеса
- **Контроль SLA заказов**: видеть, где именно заказы «застревают» и почему нарушаются сроки.
- **Снижение потерь контрактов**: выявлять проблемы до того, как клиенты начнут жаловаться.
- **Прогнозирование роста**: понимать, сколько заказов система реально способна обрабатывать.
- **Обоснование инвестиций**: данные мониторинга позволяют аргументированно принимать решения о масштабировании.

### 2.2 Для инженерной команды
- Быстрая локализация инцидентов (API, очередь, БД, расчёт стоимости).
- Понимание узких мест при росте нагрузки.
- Возможность внедрять изменения безопасно и измерять эффект.

Без мониторинга команда работает «вслепую», а проблемы обнаруживаются слишком поздно — через обращения клиентов и партнёров.

## 3. Выбор подхода к мониторингу

Для разных частей системы применяются разные подходы:

### 3.1 API (Shop, CRM, MES)
Используется подход **RED (Rate, Errors, Duration)**:
- Rate — нагрузка и профиль использования,
- Errors — стабильность и качество сервиса,
- Duration — влияние на пользовательский опыт и бизнес-процессы.

### 3.2 Очереди и фоновые процессы (RabbitMQ, расчёт цены)
Используется подход **Четыре золотых сигнала**:
- Latency — время обработки сообщений,
- Traffic — количество сообщений,
- Errors — DLQ и ошибки обработки,
- Saturation — накопление сообщений в очередях.

### 3.3 Инфраструктура и БД
Используется подход **USE (Utilization, Saturation, Errors)**:
- контроль ресурсов,
- раннее выявление исчерпания.

## 4. Выбранные метрики и их обоснование

### 4.1 RabbitMQ

#### Number of dead-letter-exchange letters
**Зачем:** выявление потерянных или «ядовитых» сообщений, приводящих к зависшим заказам.  
**Ярлыки:** queue, service, message_type, environment.

#### Number of messages in flight
**Зачем:** контроль накопления задач (особенно расчёта цены).  
**Ярлыки:** queue, priority, environment.

---

### 4.2 API (Shop / CRM / MES)

#### Number of requests (RPS)
**Зачем:** понимание нагрузки и трендов роста.  
**Ярлыки:** service, endpoint, method, environment.

#### Number of requests (RPS) per user
**Зачем:** выявление злоупотреблений API и перекоса B2B/B2C.  
**Ярлыки:** service, user_type (b2b/b2c/operator), partner_id.

#### Response time (latency)
**Зачем:** контроль пользовательского опыта и таймаутов интеграций.  
**Ярлыки:** service, endpoint, percentile (p50/p95/p99).

#### Number of HTTP 500
**Зачем:** индикатор деградации сервиса.  
**Ярлыки:** service, endpoint, error_type.

#### Number of HTTP 200
**Зачем:** базовый health-индикатор и соотношение успешных/ошибочных запросов.  
**Ярлыки:** service, endpoint.

#### Number of simultaneous sessions
**Зачем:** понимание реальной конкуренции пользователей и операторов.  
**Ярлыки:** service, user_type.

---

### 4.3 Ресурсы приложений

#### CPU % / Memory Utilisation (Shop / CRM / MES)
**Зачем:** выявление узких мест и необходимости масштабирования.  
**Ярлыки:** service, instance, environment.

---

### 4.4 Базы данных

#### Memory Utilisation (Shop DB / MES DB)
**Зачем:** раннее обнаружение деградации и риска OOM.  
**Ярлыки:** db_name, role (primary/replica).

#### Number of connections
**Зачем:** контроль исчерпания connection pool.  
**Ярлыки:** db_name, service.

#### Size of DB instance
**Зачем:** прогнозирование роста и планирование масштабирования.  
**Ярлыки:** db_name.

---

### 4.5 Хранилище файлов

#### Size of S3 storage
**Зачем:** контроль роста 3D-моделей и затрат.  
**Ярлыки:** bucket, file_type.

---

### 4.6 Дополнительные бизнес-метрики (рекомендуется)

#### Time in status (Order lifecycle)
**Зачем:** ключевая бизнес-метрика — где заказы простаивают.  
**Ярлыки:** status, order_type (b2b/b2c), priority.

#### Price calculation duration
**Зачем:** контроль самого дорогого и критичного процесса.  
**Ярлыки:** model_complexity, polygon_count_bucket, result (success/fail).

## 5. План действий (черновик ТЗ)

1. Выбрать и развернуть time-series хранилище (Prometheus / VictoriaMetrics).
2. Развернуть централизованный сбор логов (Loki / ELK).
3. Настроить экспортёры:
   - application metrics (Micrometer / OpenTelemetry),
   - RabbitMQ exporter,
   - node / cloud metrics.
4. Внедрить correlationId (orderId) во все логи и метрики.
5. Настроить Grafana:
   - дашборды API (RED),
   - дашборды очередей,
   - дашборды SLA заказов.
6. Настроить алерты и каналы оповещения (Slack / email / ticket system).
7. Обучить команду работе с дашбордами и алертами.

## 6. Показатели насыщенности и реакции (дополнительно)

### 6.1 Примеры порогов

- Messages in flight > N (расчёт цены) — риск задержек заказов.
- p95 latency MES API > X секунд — деградация операторского интерфейса.
- DB connections > 80% pool — риск отказа новых запросов.
- DLQ messages > 0 — инцидент уровня high.

### 6.2 Реакция системы

- Автоматическое создание инцидента (ticket).
- Уведомление on-call инженера.
- Для очередей — временное ограничение приёма новых B2B-заказов.
- Для CPU/Memory — добавление инстансов (или ручное масштабирование на первом этапе).

## 7. Ожидаемый эффект

- Сокращение времени обнаружения инцидентов с дней до минут.
- Снижение количества «потерянных» заказов.
- Прозрачность SLA для бизнеса.
- Осознанные решения по масштабированию и развитию системы.
